读懂 Frame 的四个参数Device &gpu 是对设备包装对象的引用，里面 device 负责创建资源，context 负责设置状态和发命令。const Options &o 是只读运行配置，例如 o.count；Metrics &m 是本帧输出记录，函数可写 m.updateMs；float dt 是模拟时间步长，单位秒。这里 dt 固定为 1/60，不是上一帧真实耗时：即使窗口只有 30 FPS，每步仍只模拟 1/60 秒。
C++ 符号不需要一次背完对象.成员 用于普通对象；指针->成员 用于指针。std::vector<Particle> 是连续粒子数组，size() 是元素数，data() 是首元素地址。auto 让编译器推导类型，不是运行时变类型。成员名结尾的下划线只是本工程命名约定。override 表示实现 Lesson 定义的虚函数；Run 调用 Frame 时实际进入当前章节的实现。std::make_unique 创建由智能指针管理的对象。
ComPtr、Get 与输出地址ComPtr<ID3D11Buffer> 管理一个 D3D 资源接口的引用生命周期。buffer.Get() 取接口指针，交给 API 使用，并不复制整块 GPU 数据。ReleaseAndGetAddressOf() 先释放旧接口，再给创建函数一个可以写入新接口指针的位置。看到 Check(...) 时先读里面的 API：Check 只是检查 HRESULT，失败时抛异常；它不会让异步 GPU 命令自动执行完成。
数据、资源、视图是三件事CPU vector 是 CPU 能直接访问的数据。ID3D11Buffer 是 D3D 资源，不能把它的接口指针当成粒子地址。SRV 是供着色器读取资源的视图；UAV 是供计算着色器写入等用途的视图。同一份粒子 Buffer 可有两种视图，不是凭空复制两份粒子。STAGING 缓冲用于 CPU 回读，DYNAMIC 缓冲用于本工程的 CPU 写入；资源创建时的用途决定后续允许的访问方式。
一颗粒子怎样变成屏幕上的点？CPU 的 Particle 是 x、y、vx、vy 四个 float，共 16 字节。HLSL 用两个 float2 表示同样布局。每步 x += vx × dt，y 同理；越过边缘后回绕。绘制时 CpuVS 从顶点缓冲取位置，GpuVS 按 SV_VertexID 从 SRV 取位置，二者都调用 MakeParticle，把 [0,1) 的坐标映射到约 [-0.95,0.95) 的裁剪空间。PS 输出颜色。速度不直接决定颜色，也不是屏幕像素坐标。
CPU 调用顺序与 GPU 执行顺序调用 Draw/Dispatch 的 C++ 代码由 CPU 执行；它安排 GPU 工作。HLSL 的 VS、PS、UpdateCS 才在 GPU 上运行。在本工程同一 Immediate Context 命令流中，先 Dispatch 再 Draw 可以表达更新后绘制的依赖，不必在两者之间让 CPU 等待。CPU/GPU 可以重叠，不等于两个 GPU 阶段一定同时执行。Flush 推动提交，但不等于完成；WaitIdle 才是本工程显式等待完成的工具。
怎样读一次测量先保证两个模式的 count、draws、frames 等输入相同，再比较 CSV 和同名 JSON 汇总。updateMs 是章节自己圈定的 CPU 区间，各章含义不同；gpu_interval_ms 是延后取得的 GPU 时间戳区间；presentMs 单独统计呈现调用。负值表示没有样本，不要计成零。先用 --validate 检查结果，再用不带 --debug 的 Release 做性能比较。一次跑得更快不能证明普遍更快，要重复运行并记录硬件、模式和参数。

CPU / GPU 流水线

先分清“调用返回”“提交”和“完成”，再讨论并行。

本章教什么

  1. Immediate Context 的调用发生在 CPU；命令经运行时与驱动缓冲后由 GPU 执行。
  2. 第 N 帧 CPU 准备可以与先前已提交的 GPU 工作重叠；每帧等待会减少这种机会。
  3. Present 和 Flush 推动执行，但函数返回不提供 GPU 工作全部完成的保证。
CPU 工作 → Draw × repeats → [模式 1：WaitIdle] → Present → 下一帧

对照模式：mode 0：正常异步执行；mode 1：每帧等待 GPU。两者绘制内容相同。

GUIDED WALKTHROUGH / 01

1．先想清楚：这个工程在演示什么？

想象游戏每帧先计算角色逻辑，再把画面任务交给显卡。本章用忙循环代替角色逻辑，用重复绘制代替可调的图形负载。窗口里的粒子保持静止是正常的：本章没有调用 Step 更新粒子。你要观察的是等待怎样改变帧耗时，而不是动画。

void Frame(Device &gpu, const Options &o, Metrics &m, float) override {
    auto start = Clock::now();
    // 模拟游戏逻辑：GPU 可以同时处理前面已提交的帧。
    volatile uint32_t work = 1;
    while (Ms(start) < o.cpuMs) {
        work = work * 1664525u + 1013904223u;
    }
    m.updateMs = Ms(start);
    for (UINT i = 0; i < o.gpuRepeats; ++i)
        renderer_.Gpu(gpu, particles_.srv.Get(), o.count, m);
    if (o.mode == 1)
        gpu.WaitIdle(); // 教学用反例：强制在每帧排空流水线。
}

01 start 与 while：制造 CPU 工作

Clock::now() 记下开始时刻，Ms(start) 返回已经过去的毫秒。o.cpuMs=4 时循环约忙碌 4 ms；这不是 Sleep，CPU 一直在算整数。volatile 让这段访问不能简单当作无用计算删掉，但它不提供线程同步。m.updateMs 只记录这一段。

02 for：安排 GPU 绘制

o.gpuRepeats=32 就调用 32 次 renderer_.Gpu，每次画 o.count 个点。重复画相同位置，视觉上不一定变复杂，工作量却增加。调用返回表示 CPU 已完成这次调用，不表示显卡已经画完。次数越多也会增加 CPU 提交成本，因此不能把它当作纯 GPU 延时旋钮。

03 if：唯一的等待差别

mode 0 跳过 WaitIdle，CPU 可以继续走向下一帧；mode 1 调用 WaitIdle，等待前面安排的 GPU 工作结束再继续。这会阻止 CPU 提前准备下一帧。Present 由外部 Run 调用，不在这里的 Frame 内。

等待的实现：EVENT、Flush 与轮询

C++
void Device::WaitIdle() {
    // 创建 EVENT 类型的查询描述，MiscFlags=0；EVENT 是完成标记，不是 Windows 线程事件句柄。
    D3D11_QUERY_DESC desc{D3D11_QUERY_EVENT, 0};
    // 用智能指针保存查询对象，离开函数后自动释放本地持有的 COM 引用。
    ComPtr<ID3D11Query> query;
    // 在当前设备上创建查询对象；此时只是分配查询资源，还没有插入完成标记。
    Check(device->CreateQuery(&desc, &query), "Create event query");
    // 把 EVENT 标记插入即时上下文命令序列；EVENT 不使用 Begin，只需要 End。
    context->End(query.Get());
    // 主动提交包括标记在内的命令，保证后面使用 DONOTFLUSH 轮询时仍能取得进展。
    context->Flush();
    // 记录 CPU 单调时钟起点，只用于计算等待超时，不是 GPU 时间戳。
    const auto start = Clock::now();
    // 无限轮询，完成时 break，出错或超时时 throw。
    for (;;) {
        // 只查是否完成：数据指针 nullptr 对应数据大小 0，不读取 BOOL 载荷。
        // DONOTFLUSH 禁止该轮询隐式触发提交；S_OK 为已完成，S_FALSE 为尚未就绪。
        HRESULT hr = context->GetData(query.Get(), nullptr, 0, D3D11_ASYNC_GETDATA_DONOTFLUSH);
        // 判断事件完成标记是否已经被 GPU 执行完成。
        if (hr == S_OK)
            // 跳出轮询，函数随后返回，调用方可以继续执行依赖此结果的 CPU 工作。
            break;
        // 传播设备丢失等真正错误；S_FALSE 不满足 FAILED，因此仍可继续等待。
        Check(hr, "WaitIdle GetData");
        // Ms(start) 返回 CPU 已等待的毫秒数，15000 即约 15 秒。
        if (Ms(start) > 15000)
            // 超时就抛异常，避免因设备或驱动异常无限等待。
            throw std::runtime_error("GPU wait timed out");
        // 让当前 CPU 线程睡眠约 1 毫秒，避免紧密空转占满核心；实际唤醒时刻取决于调度。
        std::this_thread::sleep_for(std::chrono::milliseconds(1));
    }
}

void ParticleRenderer::Gpu(Device &gpu, ID3D11ShaderResourceView *srv, uint32_t count, Metrics &m) {
    auto *ctx = gpu.context.Get();
    ctx->IASetInputLayout(nullptr);
    ctx->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_POINTLIST);

    ++m.drawCalls;
    ID3D11ShaderResourceView *nullSRV = nullptr;
    ctx->VSSetShaderResources(0, 1, &nullSRV);
}

4．拿一组具体数字手算

假设 CPU 准备恰好 6 ms、GPU 执行恰好 10 ms。第一帧从准备到执行完仍要约 16 ms。若每帧都等，第二帧只能在 16 ms 后开始；若不等，CPU 可以在 GPU 处理第一帧时准备第二帧。理想稳定输出间隔受较慢阶段限制，约 10 ms。这里忽略提交、显示和缓冲上限，只用于理解吞吐量；不是对本机帧率的承诺。

5．动手实验：改什么、看什么、如何解释

先用 CPU 负载 4 GPU 重复次数 32。比较两次报告的 CPU 帧耗时分位数和 GPU 区间。再只把 cpu-ms 改为 0：如果本来主要受 CPU 限制，现象会变化。接着恢复 4，只提高 gpu-repeat。预期每帧等待会减少跨帧重叠；若两种模式相近，检查负载是否太轻、是否开着垂直同步、是否还有其他瓶颈。

6．容易误解的地方

不要为了“保证正确”在每个 Draw 后加 WaitIdle；本章静态数据无需这样同步。也不要把更高 FPS 解读成输入延迟必然降低：排队可能增加延迟。游戏中真正依赖 GPU 结果的操作，需要明确的完成条件，而不是全面取消同步。

这一章学会的标准：能在 Frame 里指出 CPU 忙循环、GPU 工作的提交位置、强制等待位置，并解释为何单个 CPU 渲染线程也能与 GPU 重叠。

01 先看章节：updateMs 包围了什么

start 在循环之前，m.updateMs 在循环之后。因此本章 updateMs 包含多次 renderer_.Gpu 的 CPU 调用成本。后面的 WaitIdle 不在 updateMs 中，但仍在外层 CPU 帧计时中。若只盯 updateMs，可能完全漏掉等待带来的成本。

02 再看 Run：先查旧结果，再记录本帧

void GpuTimer::Begin(Device &gpu, uint64_t frame) {
    // 清除本次活动槽指针，随后通过查找空闲槽位来赋值。
    active_ = nullptr;
    // 顺序扫描所有计时槽位。
    for (auto &s : slots_)
        // pending=false 表示该槽位没有等待回收的上一帧查询，可用于本帧。
        if (!s.pending) {
            // 记录这个槽位的地址；它位于固定大小数组中，不会因数组扩容而失效。
            active_ = &s;
            // 找到第一个可用槽位即可，退出查找循环。
            break;
        }
    // 如果所有槽位都在等待 GPU，active_ 仍为空。
    if (!active_) {
        // 累计丢弃的计时样本数；丢的是本帧计时记录，不是画面帧或渲染命令。
        ++dropped;
        // 跳过本帧计时，不阻塞 CPU 等空位；这样测量本身不额外强制同步流水线。
        return;
    }
    // 把本帧编号写入槽位，保证数帧后取结果时仍知道它属于哪一帧。
    active_->frame = frame;
    active_->drawStarted = active_->drawFinished = false;
    // 开始 disjoint 区间，用来验证从此处到 End 之间的时钟是否连续并报告频率。
    gpu.context->Begin(active_->disjoint.Get());
    // 插入开始时间戳。TIMESTAMP 查询只接受 End 来记录单点时间，不调用 Begin。
    // 对象成员名 begin 表示它是“开始位置的时间戳”，并不要求使用同名 D3D API。
    gpu.context->End(active_->begin.Get());
}

void GpuTimer::Poll(Device &gpu, const std::function<void(uint64_t, double)> &consume,
                    const std::function<void(uint64_t, double)> &consumeDraw) {
    // 检查全部槽位；按槽位次序遍历，不保证回调严格按帧号递增，调用方应使用传入的帧号。
    for (auto &s : slots_)
        // 只处理 pending=true 的槽位，它表示已经 End、尚未回收查询结果。
        if (s.pending) {
            // 清零查询结果结构，准备接收 Frequency（每秒计数次数）和 Disjoint（期间是否发生不连续）。
            D3D11_QUERY_DATA_TIMESTAMP_DISJOINT dd{};
            // 尝试读取当前槽位的 disjoint 查询，输出到 dd；sizeof(dd) 给出输出结构的字节容量。
            HRESULT hr = gpu.context->GetData(s.disjoint.Get(), &dd, sizeof(dd),
                                              // DONOTFLUSH 避免为了取计时结果隐式提交命令；未就绪就留到后续帧再读取。
                                              D3D11_ASYNC_GETDATA_DONOTFLUSH);
            // 真正的失败会抛异常；查询尚未完成时返回 S_FALSE，Check 不会把它当作错误。
            Check(hr, "Poll disjoint");
            // 只有 S_OK 才说明 dd 已可用；其他非失败状态不参与本轮计算。
            if (hr != S_OK)
                // 继续外层槽位循环，当前槽位保留 pending，下次 Poll 再试，而不是在这里忙等 GPU。
                continue;
            // 准备两个 64 位整数来接收开始和结束的 GPU 时钟计数；它们目前都初始化为 0。
            UINT64 a = 0, b = 0;
            // 读取开始时间戳到 a，sizeof(a) 指定 8 字节输出；同样不触发隐式 Flush。
            hr = gpu.context->GetData(s.begin.Get(), &a, sizeof(a), D3D11_ASYNC_GETDATA_DONOTFLUSH);
            // 检查读取开始时间戳是否出现真正错误。
            Check(hr, "Poll begin");
            // 如果开始时间戳还没有准备好，本轮不能计算耗时。
            if (hr != S_OK)
                // 暂时跳过该槽位，保留其待处理状态。
                continue;
            // 读取结束时间戳到 b；它对应 End 中插入的结束标记。
            hr = gpu.context->GetData(s.end.Get(), &b, sizeof(b), D3D11_ASYNC_GETDATA_DONOTFLUSH);
            // 检查读取结束时间戳的错误状态。
            Check(hr, "Poll end");
            // 结束时间戳尚未就绪时也不等待。
            if (hr != S_OK)
                // 继续检查其他槽位，当前结果稍后再取。
                continue;
            UINT64 drawA = 0, drawB = 0;
            if (s.drawFinished) {
                hr = gpu.context->GetData(s.drawBegin.Get(), &drawA, sizeof(drawA), D3D11_ASYNC_GETDATA_DONOTFLUSH);
                Check(hr, "Poll draw begin");
                if (hr != S_OK) continue;
                hr = gpu.context->GetData(s.drawEnd.Get(), &drawB, sizeof(drawB), D3D11_ASYNC_GETDATA_DONOTFLUSH);
                Check(hr, "Poll draw end");
                if (hr != S_OK) continue;
                if (!dd.Disjoint && dd.Frequency && drawB >= drawA && consumeDraw)
                    consumeDraw(s.frame, 1000.0 * static_cast<double>(drawB - drawA) / dd.Frequency);
            }
            // 只有区间内时钟连续（Disjoint 为假）且频率非零，才能把计数差换算为有效时间。
            if (!dd.Disjoint && dd.Frequency)
                // 调用结果回调，第一个参数使用当时保存的帧号 s.frame，而不是当前 CPU 帧号。
                consume(s.frame,
                        // b-a 得到 GPU 时钟计数差，除以每秒计数频率得到秒，再乘 1000 转成毫秒。
                        // 显式转为 double 避免整数除法截断；这不是 CPU 提交 API 的耗时。
                        1000.0 * static_cast<double>(b - a) / static_cast<double>(dd.Frequency));
            // 查询数据都已取回，释放此槽位供后续帧复用；即使时钟不连续而丢弃样本，也要回收。
            s.pending = false;
        }
}

void ParticleRenderer::Cpu(Device &gpu, const std::vector<Particle> &particles, Metrics &m,
                           bool stream, bool batched) {
    if (particles.size() > capacity_)
        throw std::runtime_error("Dynamic buffer capacity exceeded");
    auto *ctx = gpu.context.Get();
    ctx->IASetInputLayout(layout_.Get());
    ctx->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_POINTLIST);
    UINT stride = sizeof(Particle), offset = 0;
    auto *vb = dynamic_.Get();
    ctx->IASetVertexBuffers(0, 1, &vb, &stride, &offset);
    ctx->VSSetShader(cpuVS_.Get(), nullptr, 0);
    ctx->PSSetShader(pixel_.Get(), nullptr, 0);
    const UINT total = static_cast<UINT>(particles.size()),
               batch = batched ? 1024u : std::max(1u, total);
    for (UINT first = 0; first < total; first += batch) {
        UINT n = std::min(batch, total - first), destination = stream ? first : 0;
        auto start = Clock::now();
        D3D11_MAPPED_SUBRESOURCE map{};
        // DISCARD 从新逻辑内容开始；NO_OVERWRITE 承诺不写 GPU 正在读取的区间。
        D3D11_MAP kind =
            (stream && first > 0) ? D3D11_MAP_WRITE_NO_OVERWRITE : D3D11_MAP_WRITE_DISCARD;
        Check(ctx->Map(dynamic_.Get(), 0, kind, 0, &map), "Map particle upload");
        memcpy(static_cast<Particle *>(map.pData) + destination, particles.data() + first,
               static_cast<size_t>(n) * sizeof(Particle));
        ctx->Unmap(dynamic_.Get(), 0);
        m.uploadMs += Ms(start);
        if (gpu.drawTimer && !batched)
            gpu.drawTimer->BeginDraw(gpu);
        ctx->Draw(n, destination);
        if (gpu.drawTimer && !batched)
            gpu.drawTimer->EndDraw(gpu);
        ++m.drawCalls;
    }
}

所有工作线程共享 data_，但写入范围互不重叠。jobs_ 在 Init 创建持久线程，不是每帧创建线程。只有主线程在汇合后调用 renderer_.Cpu 上传数据；工作线程不碰 Immediate Context。

    auto start = Clock::now();
    if (o.mode == 0)
        UpdateParticles(data_, 0, data_.size(), dt);
    else
        jobs_->Run([&](uint32_t worker) {
            size_t first = data_.size() * worker / jobs_->Size(),
                   last = data_.size() * (worker + 1) / jobs_->Size();
            UpdateParticles(data_, first, last, dt);
        }); // Run 返回意味着所有写入已完成，主线程此时才上传。

01 mode 0 是正确性基准

UpdateParticles 一次处理 [0,N)。它的数学规则与并行路径完全相同。并行优化首先要保证总共仍更新 N 个元素，而且每个恰好一次。

02 理解 lambda 与分区

[&](uint32_t worker) 是一段可调用的匿名函数，[&] 让它引用外围变量。worker 是编号 0 到 W-1。first=N×worker/W、last=N×(worker+1)/W；整数除法向下取整。UpdateParticles 只遍历 first≤i<last。线程运行期间不要 resize 数组，否则地址可能变化。

03 Run 的汇合是数据依赖

Jobs::Run 唤醒固定工作线程，等待所有任务完成才返回。此后 m.updateMs 包含唤醒、执行与汇合成本；renderer_.Cpu 才能上传完整的新一帧。这里的等待不能简单删掉，否则主线程可能上传部分旧位置、部分新位置，甚至产生数据竞争。

C++
void Jobs::Run(const std::function<void(uint32_t)> &task) {
    // 取得线程池状态锁，在同一临界区内发布本批任务及其计数信息。
    std::unique_lock<std::mutex> lock(mutex_);
    // 复制调用方的 std::function 到成员 task_；任务引用的外部对象需活到所有 worker 完成。
    task_ = task;
    // 把尚未完成的 worker 数设为线程总数，Size() 在头文件中返回 threads_.size()。
    remaining_ = Size();
    // 清空上一批的异常记录，当前批次重新开始收集错误。
    error_ = nullptr;
    // 增加批次号；各 worker 比较 generation_ 和自己的 observed，就能识别新工作。
    ++generation_;
    // 通知全部 worker；通知时仍持锁，所以它们要等下面的 wait 释放锁才能取得任务。
    work_.notify_all();
    // 等待所有 worker 都完成；wait 释放锁让它们运行，返回前再取得锁。
    // [this] 捕获本对象指针，谓词检查 remaining_==0，避免因虚假唤醒而过早返回。
    // 这里会让调用线程等待整批 CPU 工作，与 GPU 的 WaitIdle 是两种不同的同步。
    done_.wait(lock, [this] { return remaining_ == 0; });
    // 所有 worker 完成后检查是否曾有任务抛出异常；此时读取仍在 mutex_ 保护下。
    if (error_)
        // 在调用 Run 的线程重抛保存的异常；栈展开会自动释放 unique_lock，交给上层统一处理。
        std::rethrow_exception(error_);
}

void UpdateParticles(std::vector<Particle> &data, size_t first, size_t last, float dt) {
    for (size_t i = first; i < last; ++i) {
        auto &p = data[i];
        p.x += p.vx * dt;
        p.y += p.vy * dt;
        if (p.x >= 1)
            p.x -= 1;
        if (p.y >= 1)
            p.y -= 1;
        if (p.x < 0)
            p.x += 1;
        if (p.y < 0)
            p.y += 1;
    }
}

5．动手实验：改什么、看什么、如何解释

先用较小 count 比较 mode 0/1，再改成较大 count；保持 count 不变，依次设置 workers=1、2、4、8。记录 update_ms 和总 CPU 帧耗时，不只记录最快一次。预计小任务可能因线程唤醒和汇合而更慢；较大任务才可能摊薄调度成本，之后又受内存带宽或核心数量限制。

6．容易误解的地方

W 个线程不保证 W 倍加速。Amdahl 模型中，若 80% 可并行、20% 必须串行，4 线程理想加速也只有 1/(0.2+0.8/4)=2.5 倍，现实还有调度成本。若以后加入粒子间碰撞，当前“每个粒子独立”的前提不再成立，不能原样分区写入。

这一章学会的标准：能手算非整除分区，解释为何必须等待 CPU 任务结束再上传，并指出多线程慢于单线程的合理原因。第 04 章现在分别显示 GPU 帧区间与 GPU 绘制区间：后者在 CPU 上传结束后紧贴单次 Draw 前后打点，两者共享时钟有效性检查。前者可能包含供给空隙；后者仍不是纯 GPU 忙碌时间。不能用两项之差当作 CPU 耗时。CSV 的 gpu_draw_ms 保存绘制区间，其他章节未测量时为 -1。

void ComputeParticles::Step(Device &gpu, ParticleRenderer &renderer, float dt) {
    renderer.ConstantsFor(gpu, count, dt);
    auto *ctx = gpu.context.Get();
    auto *cb = renderer.ConstantBuffer();
    auto *output = uav.Get();
    ctx->CSSetConstantBuffers(0, 1, &cb);
    ctx->CSSetShader(shader.Get(), nullptr, 0);
    ctx->CSSetUnorderedAccessViews(0, 1, &output, nullptr);
    ctx->Dispatch((count + 255) / 256, 1, 1);
    // 解除 UAV 绑定后才把同一资源绑定为 VS SRV。这里没有 CPU 等待。
    ID3D11UnorderedAccessView *nullUAV = nullptr;
    ctx->CSSetUnorderedAccessViews(0, 1, &nullUAV, nullptr);
}

[numthreads(256,1,1)]
void UpdateCS(uint3 id : SV_DispatchThreadID) {
    // 向上取整派发时，最后一个工作组可能有多余线程。
    if(id.x>=particleCount) return;
    Particle p=writableParticles[id.x];
    p.position+=p.velocity*deltaTime;
    if(p.position.x>=1) p.position.x-=1;
    if(p.position.y>=1) p.position.y-=1;
    if(p.position.x<0) p.position.x+=1;
    if(p.position.y<0) p.position.y+=1;
    writableParticles[id.x]=p;
    // 每个线程独占一个元素；本算法不需要原子或组内 barrier。
}

void ReadbackRing::Poll(Device &gpu, uint64_t frame, Metrics &m) {
    auto start = Clock::now();
    for (auto &s : slots_)
        if (s.pending) {
            HRESULT hr =
                gpu.context->GetData(s.complete.Get(), nullptr, 0, D3D11_ASYNC_GETDATA_DONOTFLUSH);
            Check(hr, "Readback completion query");
            if (hr != S_OK)
                continue;
            D3D11_MAPPED_SUBRESOURCE map{};
            hr = gpu.context->Map(s.staging.Get(), 0, D3D11_MAP_READ, D3D11_MAP_FLAG_DO_NOT_WAIT,
                                  &map);
            if (hr == DXGI_ERROR_WAS_STILL_DRAWING)
                continue;
            Check(hr, "Ready readback Map");
            if (latest.empty() || s.frame >= latestFrame) {
                latest.resize(count_);
                memcpy(latest.data(), map.pData, static_cast<size_t>(count_) * sizeof(Particle));
                latestFrame = s.frame;
            }
            gpu.context->Unmap(s.staging.Get(), 0);
            s.pending = false;
            ++consumed;
        }
    m.readbackMs += Ms(start);
    if (!latest.empty())
        m.readbackAge = static_cast<int64_t>(frame - latestFrame);
}

void Jobs::Run(const std::function<void(uint32_t)> &task) {
    // 取得线程池状态锁，在同一临界区内发布本批任务及其计数信息。
    std::unique_lock<std::mutex> lock(mutex_);
    // 复制调用方的 std::function 到成员 task_；任务引用的外部对象需活到所有 worker 完成。
    task_ = task;
    // 把尚未完成的 worker 数设为线程总数，Size() 在头文件中返回 threads_.size()。
    remaining_ = Size();
    // 清空上一批的异常记录，当前批次重新开始收集错误。
    error_ = nullptr;
    // 增加批次号；各 worker 比较 generation_ 和自己的 observed，就能识别新工作。
    ++generation_;
    // 通知全部 worker；通知时仍持锁，所以它们要等下面的 wait 释放锁才能取得任务。
    work_.notify_all();
    // 等待所有 worker 都完成；wait 释放锁让它们运行，返回前再取得锁。
    // [this] 捕获本对象指针，谓词检查 remaining_==0，避免因虚假唤醒而过早返回。
    // 这里会让调用线程等待整批 CPU 工作，与 GPU 的 WaitIdle 是两种不同的同步。
    done_.wait(lock, [this] { return remaining_ == 0; });
    // 所有 worker 完成后检查是否曾有任务抛出异常；此时读取仍在 mutex_ 保护下。
    if (error_)
        // 在调用 Run 的线程重抛保存的异常；栈展开会自动释放 unique_lock，交给上层统一处理。
        std::rethrow_exception(error_);
}

actors_ 的权威状态在 CPU，particles_ 的权威状态在 GPU，二者在本实验没有本帧相互读取的依赖。因此 GPU 粒子工作可以先安排，再让 CPU 线程更新 actors_。readback_ 或 ring_.latest 只是观察 GPU 的样本，不反馈到 CPU 对象更新。

void Frame(Device &gpu, const Options &o, Metrics &m, float dt) override {
    if (steps_++ == 0)
        baseFrame_ = m.frame;
    if (o.mode == 0) {
        // 先录入独立的 GPU 工作。是否立即送达硬件仍由运行时/驱动决定。
        particles_.Step(gpu, renderer_, dt);
        renderer_.Gpu(gpu, particles_.srv.Get(), o.count, m);
        auto start = Clock::now();
        jobs_->Run([&](uint32_t id) {
            UpdateParticles(actors_, actors_.size() * id / jobs_->Size(),
                            actors_.size() * (id + 1) / jobs_->Size(), dt);
        });
        m.updateMs = Ms(start);
        ring_.Poll(gpu, m.frame, m);
        ring_.Enqueue(gpu, particles_.buffer.Get(), m.frame, m);
    } else {
        auto start = Clock::now();
        UpdateParticles(actors_, 0, actors_.size(), dt);
        m.updateMs = Ms(start);
        particles_.Step(gpu, renderer_, dt);
        renderer_.Gpu(gpu, particles_.srv.Get(), o.count, m);
        start = Clock::now();
        gpu.context->CopyResource(staging_.Get(), particles_.buffer.Get());
        D3D11_MAPPED_SUBRESOURCE map{};
        Check(gpu.context->Map(staging_.Get(), 0, D3D11_MAP_READ, 0, &map),
              "Integrated blocking readback");
        memcpy(readback_.data(), map.pData, static_cast<size_t>(o.count) * sizeof(Particle));
        gpu.context->Unmap(staging_.Get(), 0);
        m.readbackMs = Ms(start);
        m.readbackAge = 0;
    }
    // 两条路径都有一份 CPU 数据上传和一份 GPU 数据绘制，输出工作量一致。
    renderer_.Cpu(gpu, actors_, m);
}

01 mode 0 先安排 GPU 的独立工作

Step 后立刻 renderer_.Gpu，把计算和粒子绘制写入命令流。CPU 随后进入 Jobs::Run 更新 actors_，给前面 GPU 工作与 CPU 工作重叠的机会。但运行时/驱动可能暂存命令，调用顺序本身不保证硬件立刻启动。

02 CPU 工作汇合后处理旧样本

Jobs::Run 返回时所有 actors_ 更新完成。ring_.Poll 尝试消费旧数据，Enqueue 安排当前 GPU 状态的回读；满环允许丢样。m.updateMs 只包围 CPU 任务执行和汇合，不是整个并行分支。

03 mode 1 把更新和等待放到关键路径

先单线程 UpdateParticles，再安排 GPU 更新和绘制，随后 CopyResource 并立即 Map。CPU 在拿到当前 GPU 数据前不能继续走到后面的演员上传。这样把串行 CPU 更新与立即回读等待都放入当前帧流程。

void Jobs::Run(const std::function<void(uint32_t)> &task) {
    // 取得线程池状态锁，在同一临界区内发布本批任务及其计数信息。
    std::unique_lock<std::mutex> lock(mutex_);
    // 复制调用方的 std::function 到成员 task_；任务引用的外部对象需活到所有 worker 完成。
    task_ = task;
    // 把尚未完成的 worker 数设为线程总数，Size() 在头文件中返回 threads_.size()。
    remaining_ = Size();
    // 清空上一批的异常记录，当前批次重新开始收集错误。
    error_ = nullptr;
    // 增加批次号；各 worker 比较 generation_ 和自己的 observed，就能识别新工作。
    ++generation_;
    // 通知全部 worker；通知时仍持锁，所以它们要等下面的 wait 释放锁才能取得任务。
    work_.notify_all();
    // 等待所有 worker 都完成；wait 释放锁让它们运行，返回前再取得锁。
    // [this] 捕获本对象指针，谓词检查 remaining_==0，避免因虚假唤醒而过早返回。
    // 这里会让调用线程等待整批 CPU 工作，与 GPU 的 WaitIdle 是两种不同的同步。
    done_.wait(lock, [this] { return remaining_ == 0; });
    // 所有 worker 完成后检查是否曾有任务抛出异常；此时读取仍在 mutex_ 保护下。
    if (error_)
        // 在调用 Run 的线程重抛保存的异常；栈展开会自动释放 unique_lock，交给上层统一处理。
        std::rethrow_exception(error_);
}

void ReadbackRing::Poll(Device &gpu, uint64_t frame, Metrics &m) {
    auto start = Clock::now();
    for (auto &s : slots_)
        if (s.pending) {
            HRESULT hr =
                gpu.context->GetData(s.complete.Get(), nullptr, 0, D3D11_ASYNC_GETDATA_DONOTFLUSH);
            Check(hr, "Readback completion query");
            if (hr != S_OK)
                continue;
            D3D11_MAPPED_SUBRESOURCE map{};
            hr = gpu.context->Map(s.staging.Get(), 0, D3D11_MAP_READ, D3D11_MAP_FLAG_DO_NOT_WAIT,
                                  &map);
            if (hr == DXGI_ERROR_WAS_STILL_DRAWING)
                continue;
            Check(hr, "Ready readback Map");
            if (latest.empty() || s.frame >= latestFrame) {
                latest.resize(count_);
                memcpy(latest.data(), map.pData, static_cast<size_t>(count_) * sizeof(Particle));
                latestFrame = s.frame;
            }
            gpu.context->Unmap(s.staging.Get(), 0);
            s.pending = false;
            ++consumed;
        }
    m.readbackMs += Ms(start);
    if (!latest.empty())
        m.readbackAge = static_cast<int64_t>(frame - latestFrame);
}

4．拿一组具体数字手算

把一帧写成依赖链：CPU 对象更新 → 上传 → CPU 对象绘制；GPU 粒子更新 → GPU 粒子绘制，且更新 → 复制 → 完成后读样本。两条更新链之间没有箭头，所以能尝试重叠。假设独立 CPU 更新耗时 C、GPU 工作耗时 G，它们完全重叠的理想区间是 max(C,G)；整个帧还包括上传、提交、绘制和呈现，不能直接把 max(C,G) 当完整帧时间。

5．动手实验：改什么、看什么、如何解释

固定 count 和 workers，对照两种模式的总 CPU 帧耗时、GPU 区间、update_ms、readback_ms、帧龄及丢样。再在 mode 0 下只改 workers，观察 CPU 任务变化。两模式同时改变 CPU 调度与回读策略，所以总收益不能全归因于其中一项；结合第 04、06 章的单因素实验解释结果。

6．容易误解的地方

两种模式的核心更新和绘制量相同，但样本消费时效和频率不同：mode 0 可延迟或丢样，mode 1 每帧要当前结果。若真实游戏中 actors_ 必须立刻依赖本帧 GPU 碰撞结果，两条链就不再独立，不能照抄这个顺序。优化前先画数据依赖，比先加线程更重要。

这一章学会的标准：能独立画出本章依赖图，说明每处等待为何存在，并写出性能结论的适用条件，而不只说“并行更快”。

MATH / MEANING BEFORE NUMBERS

公式、单位与适用条件

先写出前提，再代入数值。模型给出解释框架，最终结论仍要看正确性和测量。

帧流水线

T串行 = C + G；T稳态 ≈ max(C,G)；FPS ≈ 1000 / T(ms)

C/G 为每帧 CPU/GPU 阶段毫秒。只适用于充分重叠、无额外节流和依赖成本的理想两阶段模型。算例：6 + 10 = 16 ms；max(6,10) = 10 ms。不是端到端延迟公式。

GPU 时间戳

T(ms) = 1000 × (B − A) / F

A/B 是同一有效区间的 tick，F 单位为 tick/s；Disjoint=false、F>0。不能混合 CPU 时间戳。算例：Δ=250000 tick，F=10⁹ tick/s → 0.25 ms。

CPU 分区

firstᵢ=⌊Ni/W⌋；lastᵢ=⌊N(i+1)/W⌋

N 为元素数，W 为线程数，i∈[0,W)。区间左闭右开，连续且不重叠。算例：10003 / 3 → 3334、3334、3335。

GPU 工作组

G=⌈N/B⌉=⌊(N+B−1)/B⌋；多余线程=G×B−N

N 为粒子数，B 为每组逻辑线程数。工程当前 B=256。整数运算前须保证加法不溢出。算例：N=10003、B=256 → G=40，多余 237。

粒子积分与回绕

p′=p+vΔt；p″=p′−⌊p′⌋（理想周期映射）

p 为归一化位置，v 为位置/s，Δt 为秒。工程用 if 加减一次实现，在小步长和给定速度下等价；大步长跨越多圈不再等价。算例：p=0.9995、v=0.06、Δt=1/60 → p′=1.0005 → p″=0.0005。

数据量与偏移

缓冲 B=16N；字节偏移=16×元素偏移；MiB=B/2²⁰

Particle 是四个 32-bit float，stride=16 B。这里的 B 指字节数，不是上一式的每组线程数。算例：65536 个粒子=1048576 B=1 MiB；4 个 staging 数据区约 4 MiB。

上传批次与绘制

Draw 数=⌈N/1024⌉；n=min(1024,N−first)

仅指第 3 章分块上传路径；一般 Cpu/Gpu 粒子路径一次 Draw。算例：10003 个粒子 → 10 次 Draw，尾批 787。

回读年龄与历史参考

age=frame−latestFrame；历史步数=latestFrame−baseFrame+1

源帧按更新后的状态复制；因此源帧 0 已经包含第一次更新。切模式后用新基准。算例：base=100、latest=117 → 历史参考执行 18 步。

最大允许误差

e位置=min(|a−b|,1−|a−b|)；e速度=|va−vb|

位置在 [0,1) 的周期域；全体位置/速度误差取最大值。本工程阈值为 0.0002。算例：0.99999 与 0.00001 的周期距离为 0.00002，不是 0.99998。

加速比与串行上限

S=T旧/T新；Amdahl：S(W)=1/((1−p)+p/W)

p 是基线中可并行部分比例，W 是理想并行度；忽略调度、通信和带宽约束，真实结果可能更低。算例：p=0.75、W=4 → 2.286 倍；W→∞ 的上限为 4 倍。

网格与坐标

side=⌈√D⌉；列=cell mod side；行=⌊cell/side⌋

D 为三角形 Draw 数，每单元 3 个顶点；最终 NDC xy=1.9×p−0.95。算例：D=257 → side=17；第 256 个单元位于列 1、行 15（从 0 开始）。

本工程分位数

Qp=排序数组[⌊(n−1)p⌋]；预热=min(30,⌊frames/4⌋)

这是实现采用的下标法，不是插值分位数。偶数样本中位数取下侧，不平均中间两个值。算例：[1,2,3,4] 的 p=0.5 → 下标 1 → 2。

 39    }  40    void Frame(Device &gpu, const Options &o, Metrics &m, float dt) override {  41        if (steps_++ == 0)  42            baseFrame_ = m.frame;  43        if (o.mode == 0) {  44            // 先录入独立的 GPU 工作。是否立即送达硬件仍由运行时/驱动决定。  45            particles_.Step(gpu, renderer_, dt);  46            renderer_.Gpu(gpu, particles_.srv.Get(), o.count, m);  47            auto start = Clock::now();  48            jobs_->Run([&](uint32_t id) {  49                UpdateParticles(actors_, actors_.size() * id / jobs_->Size(),  50                                actors_.size() * (id + 1) / jobs_->Size(), dt);  51            });  52            m.updateMs = Ms(start);  53            ring_.Poll(gpu, m.frame, m);  54            ring_.Enqueue(gpu, particles_.buffer.Get(), m.frame, m);  55        } else {  56            auto start = Clock::now();  57            UpdateParticles(actors_, 0, actors_.size(), dt);  58            m.updateMs = Ms(start);  59            particles_.Step(gpu, renderer_, dt);  60            renderer_.Gpu(gpu, particles_.srv.Get(), o.count, m);  61            start = Clock::now();  62            gpu.context->CopyResource(staging_.Get(), particles_.buffer.Get());  63            D3D11_MAPPED_SUBRESOURCE map{};  64            Check(gpu.context->Map(staging_.Get(), 0, D3D11_MAP_READ, 0, &map),  65                  "Integrated blocking readback");  66            memcpy(readback_.data(), map.pData, static_cast<size_t>(o.count) * sizeof(Particle));  67            gpu.context->Unmap(staging_.Get(), 0);  68            m.readbackMs = Ms(start);  69            m.readbackAge = 0;  70        }  71        // 两条路径都有一份 CPU 数据上传和一份 GPU 数据绘制，输出工作量一致。  72        renderer_.Cpu(gpu, actors_, m);  73    }  74    void Validate(Device &gpu, const Options &o, uint64_t frames) override {  75        auto expected = InitialParticles(o.count);  76        for (uint64_t i = 0; i < frames; ++i)  77            UpdateParticles(expected, 0, expected.size(), 1.0f / 60.0f);  78        VerifyParticles(actors_, expected);  79        VerifyParticles(particles_.ReadBlocking(gpu), expected);  80        if (o.mode == 1)  81            VerifyParticles(readback_, expected);  82        else {  83            Metrics drain;  84            ring_.Poll(gpu, baseFrame_ + frames, drain);  85            if (!ring_.consumed)  86                throw std::runtime_error("Integrated readback ring never completed");  87            auto historical = InitialParticles(o.count);  88            for (uint64_t i = 0; i <= ring_.latestFrame - baseFrame_; ++i)  89                UpdateParticles(historical, 0, historical.size(), 1.0f / 60.0f);  90            VerifyParticles(ring_.latest, historical);  91        }  92    }  93};  94int main(int argc, char **argv) {  95    return Run(argc, argv, std::make_unique<Integrated>());  96}
