# CPU 并发实验室：把多核的工作过程和收益一起看见

双击 **[Start-Lab.cmd](Start-Lab.cmd)**，点击 **一键对照**。这是独立的 C++17 / Win32 工程：CPU 真正计算一张有球体、金属反射和棋盘地面的图像，逐块显示计算结果，并画出每个工作线程的任务时间线。

## 为什么换一个任务

原课程第 04 章的粒子更新主要是数组读写、加法和边界判断。它适合学习分区与汇合，但每个元素的计算太少，线程唤醒、内存带宽、后续上传和呈现都可能影响观察。增加线程数并不能保证收益。

新工程选择 CPU 路径追踪：每个像素发出多条光线，求交、反射、累积颜色。更多采样会改善图像噪声，增加的是有用的计算；没有用 Sleep 或空转来制造耗时。CPU 不调用 GPU 来算这些像素；Win32/GDI 只负责显示，桌面合成仍可能由系统 GPU 执行。

一个实验同时回答三个问题：**是否有多个任务重叠？是否实际占用了多个逻辑处理器？是否更快完成了同一份工作？** 三者分别看时间线、线程 CPU 时间和串行对照。

## 三种策略

| 策略 | 如何分配同一批图块 | 适合观察什么 |
|---|---|---|
| 单线程 | W0 顺序执行全部图块 | 相同算法的串行基准 |
| 静态分块 | 每个 worker 预分配连续的图块区间 | 天空便宜、地面和多次反射昂贵；工作量分布不均会形成尾部等待 |
| 动态取任务 | worker 用原子递增领取下一个图块，算完再领 | 忙的线程继续工作，空闲线程接手剩余任务；过细图块会增加调度和记录开销 |

静态分块并非普遍较差，动态调度也不是总能更快。本例刻意保留自然存在的空间计算量差异，便于理解负载均衡。动态领取是一个共享索引，不是工作窃取；没有必要为这个独立任务集合先引入完整 DAG 调度器。

## 窗口怎么用

1. 选择工作线程数、每像素采样数和图块边长。窗口固定 640×360、最多 5 次反射，改变窗口尺寸不会改变计算量。
2. 点击“一键对照”，自动先跑串行，再跑当前并行策略；若选的是单线程，则自动选择动态策略进行对照。
3. 看彩色边框和下面的时间线。同一种颜色对应同一 worker；超过 8 个 worker 时点“下一组线程”翻页。
4. 看完成后的加速比和平均 CPU 并行度。采样数越高，越容易观察成图过程；可以选 256。低采样用于观察小任务开销。
5. 切换静态/动态策略重跑。同一工作量的串行基准会保留；改变采样数后旧基准不参与加速比计算。图块大小不改变总光线工作量。
6. “取消”在像素边界协作停止，不强杀工作线程；取消结果不作为完整结果比较。“导出结果”生成 BMP 图像、JSON 指标和 Chrome Trace Event 格式的逐块时间线。

运行期间参数锁定，避免把新参数和旧任务混合。每个像素有独立随机种子，因此线程数、任务顺序和图块大小不改变最终像素。GUI 和 CLI 都比较完整像素数组；checksum 只是额外的报告字段，不作为唯一正确性证据。

## 测量口径

| 指标 | 定义 | 不能推导出的结论 |
|---|---|---|
| 墙钟时间 T | 发布任务之前到最后一个 worker 汇合，使用 QPC | 不是 CPU 总工作时间；不含线程创建、图像分配、最后的校验、导出和显示 |
| 线程 CPU 总时间 C | 所有 worker 的用户态 + 内核态执行时间增量，使用 GetThreadTimes | 不包括 GUI 线程；不是物理核心数，不是频率或 IPC |
| 平均 CPU 并行度 C/T | 这批工作平均消耗的逻辑处理器执行时间 | SMT 两个逻辑线程不等于两颗独立物理核心；也不是整个系统的 CPU 使用率 |
| 加速比 S | 相同输入的单线程 T1 / 当前 Tp | 不能用时间线重叠或线程数量代替 |
| 效率 E | S / 工作线程数 | 不是处理器利用率 |
| 彩色时间线 | 每个图块开始到结束的墙钟区间 | 线程可能在区间内被抢占；条带重叠不等于同时在核上运行 |

**GetThreadTimes 的表示单位为 100ns，不等于记账精度为 100ns。** 本机短任务能出现 C/T 略大于线程数，例如约 0.21 秒的任务得到 8.25。保留原始值，不能通过强行截断制造精确感。应提高采样数、延长负载并重复测量；GUI 的短时结果只用于观察。CPU 时间汇总在 worker 完成整批工作时发布，运行中不显示不完整的并行度。

固定线程池在批次之间使用条件变量等待。串行模式仍走同一批次机制，只由 W0 算图。GUI 的刷新、操作系统调度、睿频、温度、电源模式和其他进程都会影响结果；正式比较使用 Release 命令行，关闭其他计算负载。线程创建虽然排除在计时外，线程唤醒和汇合包含在内。trace 每图块打点和原子领取的成本也包含在内。

## 可复现实验

双击 **[Run-Benchmark.cmd](Run-Benchmark.cmd)**，默认测试串行以及静态/动态 1、2、4、8 线程（上限按机器逻辑处理器数取至 8），每组 3 次。也可执行：

```powershell
cd D:\program_data\cpugpu\cpu-parallel-lab
.\build\Release\cpu_benchmark.exe --width 640 --height 360 --samples 256 --workers 8 --repeats 3 --output out\benchmark-long
```

每个池先用完整负载预热，预热不写入统计；每轮反转配置顺序以缓解固定先后顺序偏差。汇总包含中位数、最小值、最大值、加速比和效率。只有 3 轮，不声称统计显著性或最佳线程数。

输出包括：

- `samples.csv`：每轮原始结果，含负载参数。
- `summary.csv`：每配置的中位数、范围和加速比。
- `serial-1.json`、`dynamic-8.json` 等：最后一轮完整参数和每线程 CPU 时间。
- `*.trace.json`：最后一轮逐块时间线，可导入支持 Chrome Trace Event 格式的查看器。
- `render.bmp`：串行计算的完整图像，所有其他配置均已逐像素比对。

### 推荐的三个实验

1. **扩展性**：固定负载，比较 1/2/4/8 线程，观察加速比何时开始低于线程数。4 核 8 线程不应预期 8 倍加速。
2. **负载均衡**：固定线程数和图块大小，切换静态/动态。看早早完成的线程和最后拖长的线程，以及相同像素的总完成时间。
3. **任务粒度**：固定采样数和线程数，分别用 tile 4、16、32、128、256。太小增加调度、时钟记录和缓存争用；太大减少任务数、增加尾部等待。没有预设“最佳 tile”。

### 为什么没有数据竞争

配置、图块几何和图像容量在启动前固定；计算过程中不 resize。每图块只分配给一个 worker，图块覆盖的像素互不重叠。渲染线程完成图块后 `state.store(2, release)`；显示线程只在 `load(acquire)==2` 后读取这些像素。尚在计算的像素不读取。

任务开始时间和 owner 在 `state=1` 前发布，结束时间在 `state=2/3` 前发布；`Poll` 不复制正在写入的结束时间。线程 CPU 统计、批次结束和异常在互斥锁下汇合。条件变量使用谓词等待，避免丢失唤醒和虚假唤醒。owner 不能并发调用 Start；主动取消和析构都协作收尾。
