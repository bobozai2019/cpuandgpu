CPU PARALLEL LAB / C++17 / WINDOWS

把“开了很多线程”
变成能验证的多核协作

本工程让 CPU 计算一张带有反射和漫反射的图像。每个图块都是实际任务，每条时间线都来自真实计时。先单线程完成相同画面，再改变调度方式，观察完成时间和 CPU 执行时间。

完整工程说明与测量口径 · 本机验证记录 · 调度器源码 · 计算源码

01 / 看任务

图块按 worker 着色；时间线显示每个任务何时开始、结束。重叠表明任务并发推进。

02 / 看执行

操作系统记录每条工作线程实际消耗的 CPU 时间。除以墙钟时间，估算平均逻辑 CPU 并行度。

03 / 看收益

串行时间除以并行时间，才是加速比。所有配置的最终像素必须完全一致。

先跑这一组

  1. 双击 Start-Lab.cmd。保持“动态取任务”，选择 4 或 8 个工作线程。
  2. 点“一键对照”：先串行，再并行。提高采样数到 128 或 256，便于观察成图过程。
  3. 切换“静态分块”，重跑。天空通常更容易算，地面和反射区域更难算；观察最后仍在工作的线程。
  4. 固定其他参数，把图块边长从 4 改为 32、128、256，观察调度开销和尾部等待。
  5. 用 Run-Benchmark.cmd 收集多轮数据。窗口刷新也有成本，正式测量以 CLI 为准。

同一份工作，三种组织方法

策略分配方式可能出现的现象
单线程W0 依次执行全部图块作为同一算法的参考结果和耗时基准
静态分块每线程预先分到连续区间任务数量相近，但求交与反射工作量不同；部分线程提前结束
动态取任务算完一块，用原子索引再领一块减少工作量不均的尾部等待；块太小则增加领取与计时开销

下面是 Amdahl 理论计算器，不是实时硬件测量。假设总工作量固定，可并行部分理想均分，并且没有额外调度或内存成本。

读代码的顺序

第一步：RenderTile — 哪些数据能并行写？

每个图块只覆盖自己的矩形像素。像素的随机数种子由像素坐标决定，所有采样在同一线程内按固定顺序求和。更换线程或图块划分不会改变结果。

pixel → 固定种子 → 多条光线 → 求交和反射 → 颜色平均 → 独占像素
第二步：Worker — 多线程在哪里开始分工？

所有 worker 等待带谓词的条件变量。Start 发布新一代批次，线程醒来。静态方式直接计算自己的区间；动态方式对共享 next 做 fetch_add(1)，取得唯一图块编号。下一次取任务发生在当前图块计算完成后。

while (!cancel) {
    index = next.fetch_add(1);
    if (index >= tileCount) break;
    Process(index, workerId);
}

这里的原子操作用于唯一分配，不承担像素结果的发布；两个同步责任分别处理。

第三步：Process / Image — 如何让显示线程安全读取？

worker 完成图块后，用 release 发布 state=2。显示线程读到 acquire 的完成状态，才复制该块像素。未完成的块始终不读取，避免一边写像素一边显示造成数据竞争。取消中的块不会当成完整结果。

第四步：最后一个 worker — 何时能算最终耗时？

每线程在执行批次前后读取 CPU 时间；结束时在锁下提交统计，并减少剩余 worker 数。最后一个 worker 记录墙钟结束时刻、标记批次完成并唤醒等待者。完整像素比较和导出发生在计时结束之后。

容易误读的四个数字

指标含义与边界
线程数量只是可以参与计算的工作线程数；不等于实际同时执行数。
时间线重叠任务墙钟区间相交，期间可能发生抢占或等待；不能据此证明使用了几个物理核心。
CPU 时间 / 墙钟平均消耗的逻辑 CPU 执行时间。短任务有记账误差，可能略高于线程数；不强行截断原始值。
加速比相同输入的串行时间 / 当前时间。4 核 8 线程的硬件不能预设为 8 倍加速。

把结果留下来

.\build\Release\cpu_benchmark.exe --width 640 --height 360 --samples 256 --workers 8 --repeats 3 --output out\benchmark-long

输出每轮 CSV、汇总 CSV、每线程 JSON、BMP 图像和 trace。各配置预热后运行，每轮反转顺序；像素比较失败时程序返回非零退出码。比较 tile 大小时，其他参数保持相同。

实现为独立 C++17 工程，Windows SDK / MSVC，无第三方下载依赖。计时定义依据 GetThreadTimes 和 QPC。详细限制、验证结果和源码入口以 README 为准。
