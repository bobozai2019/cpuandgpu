01

线程复用：把任务交给长期工作的线程

线程是执行者，任务是待执行的一段工作。 每个任务新建一个线程，会重复支付创建、栈空间和调度成本；线程池预先创建少量线程，任务到来时放入队列，由空闲线程反复取走执行。

主线程 / 生产者→ 提交受锁保护的任务队列→ 取出W1 / W2 / … 工作线程→ 写回结果或异常

并发是多个任务都在推进；并行是同一时刻在不同 CPU 执行资源上运行。工作线程数不是 CPU 核心数，开更多线程不保证更快。FIFO 只约束队列取出顺序，不保证开始执行或完成顺序，也不保证调度公平性。

02

原子操作：为什么 count++ 会丢更新

逻辑上的 count++ 可拆成“读取旧值 → 加 1 → 写回”。两个线程同时读到 0，再各自写入 1，最终只有 1。原子读改写把这组更新作为不可分割的操作，避免两个更新互相覆盖。

交互实验 · 让两个执行者各加一次

两个执行者各加 1，最终应为 2。
C# 的普通自增不是原子操作，volatile 也不会把 ++ 变成原子读改写。演示使用安全的顺序步骤重放错误交错；工程中的真实多线程计数只采用正确同步。
一个计数器的原子更新
long count = 0;
Interlocked.Increment(ref count);
long progress = Interlocked.Read(ref count);

Interlocked.Increment 返回更新后的新值；Interlocked.Read 用于安全读取 long。Interlocked.CompareExchange 可在当前值等于预期值时写入新值，并返回旧值，适合实现条件更新。它们处理单个存储位置，不能自动把几个字段组成一个事务。

原子性、可见性、顺序性分别问什么

概念要回答的问题本工程中的做法
原子性另一个执行者能否插入一次读改写的中间？计数器使用原子增量；队列操作使用锁。
可见性一个线程写好的结果，另一个线程何时可以读取？通过结果句柄等待完成，或使用同一把锁建立同步。
顺序性普通数据写入与“数据准备好了”的标记，是否有正确先后关系？任务交接由队列锁完成；不要用进度计数替代结果协议。

扩展：Volatile.Read/Write 约束特定读取与写入的可见性和重排序，但 volatile 字段的 ++ 仍不具备原子性。C# 不直接提供 C++ 那样的 memory_order 参数；不要机械翻译 relaxed。

03

mutex：保护一组必须一起成立的事实

队列中的 empty → front → pop 必须整体互斥。如果只把长度改成原子变量，两个消费者仍可能取走同一元素。mutex 保护的是访问协议：所有接触这些共享状态的路径都要遵守同一把锁。

用作用域管理锁的生命周期
private readonly object gate = new();
lock (gate)
{
    // 在同一个临界区里完成检查和修改。
} // 正常离开或抛异常都会释放 Monitor 锁。
// 本课程有 Monitor.Wait/PulseAll，必须使用同一个 object gate。
工具适合保护什么本课程的选择
std::mutex / C# lock(object)进程内多个字段构成的不变量保护队列、关闭标志和 active。
std::atomic / Interlocked一个计数或一个条件更新对外提供无需取得队列锁的进度读取。
条件变量 / Monitor.Wait条件尚未满足时释放锁并阻塞等待等待可取任务，或等待全部空闲。
C# System.Threading.Mutex需要操作系统互斥量，例如命名的跨进程互斥本课程队列在进程内，选择 lock/Monitor；Mutex 用 WaitOne/ReleaseMutex，不能直接替换本实现的 Monitor 协议。
Semaphore / SemaphoreSlim限制可同时进入的数量，或表示可消费的许可可用于有界队列；单凭许可不能代替队列状态的互斥保护。

对 object 使用 lock 时采用 Monitor，允许同一线程重入。现代 C# 还支持 System.Threading.Lock 专用类型，但它与 Monitor 的等待协议不能混用；本例明确使用私有 object。不要锁 this、字符串或公开对象，否则外部代码可能参与同一把锁。

临界区要短：只在锁内操作任务队列与状态；执行用户函数、等待结果、Join 线程都在队列锁外进行。否则会把线程池串行化，甚至造成死锁。
04

条件等待：检查条件，而不是记住通知

队列没有任务时，worker 不应该不断循环抢锁、检查、sleep。它先持锁查看条件，条件不满足就进入等待：释放锁并阻塞，醒来后重新取得锁，再检查条件。

实际 WorkerLoop 的取任务片段
lock (_gate)
{
    while (_queue.Count == 0 && !_stopping)
        Monitor.Wait(_gate);
    if (_stopping && _queue.Count == 0) return;
    job = _queue.Dequeue();
    ++_active;
}
  1. 先取得队列锁。保证看到的队列与关闭状态互相一致。
  2. 条件不满足就等待。等待过程中不持有队列锁，生产者才能入队；等待协议连接“释放锁”和“开始等待”，避免自己制造检查与睡眠之间的空隙。
  3. 醒来后重新判断。收到通知仅表示可以重新竞争锁。另一个 worker 可能先取走任务；因此用 while，不能只用 if。
  4. 只有关闭且队列为空时退出。关闭但队列不空时，继续消费已接收任务。

通知不储存“任务完成凭证”。若通知发生时没有等待者，下一次等待也不会自动消费旧通知。真实依据一直是锁保护下的条件，生产者必须在同一同步协议中修改条件。

本实现让 worker 和 WaitIdle 调用者共用 _gate 的 Monitor 等待集合。提交时使用 PulseAll，避免只唤醒了等待“空闲”的调用者而没有唤醒 worker。PulseAll 必须在持有该 Monitor 锁时调用；被通知者仍需等当前持锁者释放锁。

worker 在锁内弹出任务并增加 active，之后释放锁。其他 worker 此时可以继续取走其他任务，所以多个任务能够并行执行。取出与执行 · 源码 L101 ↗

04 · 执行：结果与异常都返回给调用者

TaskCompletionSource 把业务异常放入 Task，GetAwaiter().GetResult() 或 await 会观察到它。本页控制台示例使用同步等待方便跟读；UI 或异步调用链中宜 await，避免阻塞界面。Task 代表操作结果，不意味着每个 Task 都拥有一条线程。

Task 完成与线程池完成记账之间存在一个很短的窗口：结果已经可读，但 active 还未减为 0。需要一致统计时，先调用 WaitIdle()。

05 · 完成记账：维护不变量

在队列锁内增加 completed，减少 active；当队列空且 active==0，通知空闲等待者。持队列锁取得的快照满足：

submitted = queued + active + completed

completed 的更新仍放在队列锁内，是为了让统计快照一致；它使用原子类型，是为了让独立的进度 getter 可以不取队列锁。这不是无锁队列。统计快照 · 源码 L92 ↗

生命周期、异常与死锁边界

拒绝新任务，处理旧任务→ Join 全部完成Stopped

图中的三个名字是教学状态；实现使用 stopping 标志和 Join 过程表达它们，没有额外的状态枚举。关闭线性化点是持有队列锁时把 stopping 设为 true：在它前面入队成功的任务会执行，在它后面尝试入队的任务被拒绝。

为什么不能持队列锁 Join

关闭者持锁等 worker 退出；worker 需要同一把锁取任务或检查退出条件。两边互等，永远无法前进。实现只持独立关闭锁 Join。

为什么 worker 不能等待自身空闲

它本身就占着 active，只有它返回 active 才会减少。实现使用线程局部标记检测同池 WaitIdle/Shutdown 并抛异常。

嵌套等待仍然可能饿死整个池

假设只有 1 个 worker：父任务向同池提交子任务，接着等待子任务结果；子任务还在队列里，唯一 worker 却被父任务占着。N 个 worker 全部这么做也会停住。自身等待检查无法识别任意 future/Task 依赖图；应由池外组织依赖，或使用专门的任务调度机制。

捕获的数据必须活到任务使用结束

for 循环内先创建 int index = i，再捕获 index；直接捕获循环变量 i 会共享同一个变量。GC 保证对象仍被引用时不回收，不保证字段访问线程安全；Dispose 的资源也可能提前失效。using 必须覆盖任务使用资源的整个时期。

教学实现边界：固定线程数、无界队列、同步任务、优雅排空；不提供取消、超时关闭、优先级、工作窃取或背压。任务阻塞永不返回时，关闭也会一直等待。无界队列可能积压内存，生产系统需设计容量与拒绝策略。

本实现拒绝常见 Task/ValueTask 返回类型与直接 async void 委托；不要通过 object、同步包装或自定义 awaitable 绕过同步契约。它不流动 ExecutionContext，不等价于 .NET 内置 ThreadPool。日常 CPU 并行优先评估 Task.Run / Parallel；I/O 等待通常使用原生 async API。自定义池用于理解机制和明确需要独立线程的场景。

08

练习与常见误区

01 · 为什么不能只检查 queue.empty()？

worker 会先把任务取出再执行，此时队列可能已空。必须同时检查 active==0；测试 empty queue vs active task 专门覆盖它。

02 · 把任务体移到队列锁内会怎样？

同一时刻只有一个任务能执行，并行度退化；若任务又提交到本池，C++ 普通 mutex 的递归加锁还会导致死锁风险。无论语言，都应把用户代码放在锁外。

03 · completed==submitted 能否随时作为销毁对象的条件？

不能独立读取两个计数就推断稳定空闲；生产者可能继续提交，结果和记账也有短暂时间差。用队列锁下的不变量、WaitIdle 的观察，或 Shutdown 停止接收并 Join；销毁还必须由外部所有者协调其他访问者。

04 · 如何给队列增加容量上限？

在队列锁内检查容量；满时先选择明确策略：拒绝提交、阻塞生产者或等待超时。阻塞生产者需要另一个“有空位”的条件；关闭必须唤醒它们，worker 提交也要考虑池耗尽死锁。增加测试：满队列、并发生产者、关闭时仍有生产者等待。

05 · 如何减少计数器上的竞争？

每个任务使用局部变量完成 iterations 次累计，结束时只加一次到共享计数器。锁/原子更新从 tasks×iterations 次降到 tasks 次，但仍要验证总和。

06 · 为什么关闭不等于取消？

当前契约承诺排空已接收的任务。取消需要另行定义未执行任务的结果状态、运行中任务的协作检查和取消与成功的竞态。不能安全地强杀任意正在执行的线程。

建议扩展顺序：增加每任务局部计数 → 实现拒绝策略的有界队列 → 为关闭竞态补测试 → 最后才考虑优先级、取消和更复杂调度。每加一个状态，都要回答它由哪把锁保护、由谁通知、在关闭时如何终结。
